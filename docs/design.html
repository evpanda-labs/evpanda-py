evpanda-py

A passive OCPI / OCPP capture SDK that lives inside someone else's production process. It records protocol traffic, buffers it in memory, and ships it in batches — while guaranteeing it never blocks, never raises, and never grows without bound.

This document explains how the SDK is put together, what happens to a captured message between your handler and the ingestion API, and how to wire it into a service. Read Part I and Part II to understand the machine; read Part III if you just need to use it.

The design tracks evpanda-go, which is the reference implementation — same layering, same pipeline, same wire records, same names wherever a Python name can carry them. Where Python diverges it is deliberate, and §A lists every divergence in one place. Two of them are worth knowing up front: bytes is immutable, so the ownership dance the Go SDK performs on every capture mostly disappears; and a Python process forks and exits in ways a Go one does not, so the SDK has to survive both.

Part I

Architecture

1Constraints that shaped everything

This SDK is unusual in one respect: it runs inside a customer's charging platform, on their threads, in their memory, on the hot path of their revenue-carrying traffic. Nothing it does is worth a degraded charging session. Four rules follow from that, and every design decision below is downstream of them.

Invariant 1

Capture never blocks. A capture call validates, normalizes, and appends to a deque — no I/O, no queue that can be full, no lock held across a syscall. If the upstream is down, capture cost does not change.

Invariant 2

Nothing raises into the host. Every public entry point is wrapped. Capture methods return None, so an exception has nowhere to surface and is swallowed, counted, and (in debug) logged; flush() and close() do the same and report through their return value.

Invariant 3

Memory is bounded, and the bound is a number you provision against. max_buffer_bytes is the ceiling on everything held awaiting delivery — 32 MiB by default, allocated on demand. Under stress the SDK evicts rather than accumulating.

Invariant 4

A bad config degrades, it does not crash. start_ocpi() / start_ocpp() always return a usable client and never raise. A bad endpoint yields an inert client carrying the reason on .error; you may log it and carry on booting.

Two consequences are worth stating plainly, because they are the trade the whole design makes. Delivery is best-effort. A batch that survives five retries and still fails is dropped, and a buffer that fills evicts its oldest entries. Losing telemetry is always preferable to slowing down a charge point. And capture is fire-and-forget: no capture method returns anything, because there is nothing a caller could usefully do with a failure.

Why start_ocpi() does not raise. Raising is the Python default, and for a library that computes something it is the right one. This library does not compute anything the host needs: if it cannot start, the correct outcome is a charging platform that boots without telemetry, not one that does not boot. So the failure is returned as state — panda.error, an exception instance you can isinstance-match or re-raise yourself — and it is logged at ERROR on the way out, so ignoring the attribute is not the same as never being told.

2Shape of the package

One package, one public module surface. Every implementation module is underscore-prefixed and re-exported from __init__.py, which makes the public API exactly the contents of evpanda.__all__ — nothing else is promised, and any of it can move without a deprecation cycle. It is the same job Go does with lowercase identifiers, done with the tool Python provides.

The two protocols meet at one place: _types.OCPIMessage and _types.OCPPMessage are the only things the buffer holds, and each knows its own accounted size. The transport maps them onto wire records with a single isinstance check — with exactly two message types and one call site, an interface would be indirection for its own sake.

2.1  Why the adapters are their own subpackage

The capture pipeline and the adapters change at different rates. The pipeline is done — a buffer, a thread, a transport, and a wire contract that only moves when the ingestion API does. Adapters accumulate framework surface indefinitely: today WSGI, ASGI, httpx and requests; tomorrow whatever a customer's CSMS is written against. Keeping them apart means the growing half cannot crowd the finished half's namespace, and help(evpanda) stays about capture.

Two of the four adapters need a third-party import, and neither may become a dependency of the SDK: nobody should install requests to capture OCPP traffic. So evpanda.ocpi imports the two stdlib adapters eagerly and the other two on first use, through a module __getattr__ (PEP 562):

ocpi/__init__.py — lazy by name, not by try/except
# Which module each lazily-imported name lives in, and what to install
# if it is missing.
_LAZY = {
    "HTTPXTransport":      ("httpx_transport", "httpx"),
    "AsyncHTTPXTransport": ("httpx_transport", "httpx"),
    "RequestsAdapter":     ("requests_adapter", "requests"),
    "instrument_session":  ("requests_adapter", "requests"),
}

def __getattr__(name: str) -> Any:
    entry = _LAZY.get(name)
    if entry is None:
        raise AttributeError(f"module {__name__!r} has no attribute {name!r}")
    module_name, extra = entry
    try:
        module = __import__(f"{__name__}.{module_name}", fromlist=[name])
    except ImportError as exc:
        raise ImportError(
            f"{__name__}.{name} needs `{extra}` — pip install 'evpanda[{extra}]'"
        ) from exc
    return getattr(module, name)

The alternative — a top-level try: import httpx / except ImportError: HTTPXTransport = None — fails in the direction that costs a user an afternoon: a missing extra turns into TypeError: 'NoneType' object is not callable at the call site. This way the error names the package and the install command, and import evpanda.ocpi stays free of third-party imports either way. Type checkers see the names through a TYPE_CHECKING block, so completion and mypy work as if they were imported normally.

2.2  The seam the adapters see

The adapters need two things from a client: the resolved per-body cap, so a streaming body is bounded as it is read rather than after it is buffered, and a live/inert check, so a closed client costs no per-request work. One method answers both.

_client.py — consumed by evpanda.ocpi
def capturing(self) -> int | None:
    """The per-body byte cap while this client is capturing, else None.

    The cap and the fact of capturing come back together deliberately:
    asked separately they could straddle a close and disagree.
    """

Go returns (maxCaptureBytes int, ok bool); Python returns int | None, which is the same two facts in the shape the language already has for them. The adapters depend on a three-method Capturer protocol rather than on OCPIClient — the two capture methods plus capturing — so they can be tested against a fake with no pipeline running, which is exactly how the adapter suites in tests/ work.

Not a leak — the documented escape hatch. Exporting capturing() and identity.valid() is not internal plumbing escaping: they are exactly what someone writing an adapter for a framework the SDK does not ship needs. Since "call capture_inbound_message yourself" is the documented answer for aiohttp, Tornado and the rest, the seam has to be public anyway.

3Concurrency model

One client owns exactly one thread. Not a pool, not one per connection — one, and it is a daemon thread, so it can never be the reason an interpreter refuses to exit. It is the only thing in the SDK that performs I/O, and the only thing that touches the transport.

Producers and the consumer meet at exactly one point — the buffer, which holds a lock for the microseconds it takes to append to a deque. Everything else about the capture path is lock-free by construction, because nothing else is shared.

The counters take a lock; they do not lean on the GIL. self._captured += 1 is three bytecodes, and on a free-threaded build (3.13+, PEP 703) two threads can interleave them and lose an increment. Since the capture path already acquires the buffer lock, one more uncontended acquisition is not what will cost the host anything — and a counter that silently under-reports during exactly the incident it exists to explain would be worse than no counter.

Capture is safe from async code. It never touches the event loop and never awaits: a capture call is a validation, a bytes reference, and a deque append, all measured in microseconds. That is what lets the ASGI middleware and the async httpx transport call it inline rather than scheduling it.

flush() and close() are the two that block, and they block for as long as the transport's bounded retry takes. From an async shutdown handler, hand them to a thread: await asyncio.to_thread(panda.close). Neither belongs on a request path — capture is already asynchronous; you do not need to flush to make it happen.

Part II

Data flow

4The pipeline, end to end

Every captured message — OCPI or OCPP, adapter or direct call — takes exactly this path. There is no second route, no fast path, no bypass.

Two things are worth noticing about where the boundary sits. First, redaction happens above it — an unredacted message is never written to the buffer, so a heap dump of a running process cannot contain a captured Authorization header. Second, the capture timestamp is stamped above it too, at chokepoint time. captured_at is when your handler saw the traffic, not when the SDK got round to shipping it, so queue delay never distorts the record.

5The chokepoint

prepare_ocpi and prepare_ocpp in _worker.py are the single place a message is checked and transformed before it enters the queue. They are pure functions: given a message they return an envelope to enqueue, or None plus the reason it was dropped. Keeping them pure and module-level is deliberate — it means there is one answer to "why was my message not captured?", and it can be unit-tested without a client, a server, or a thread.

_worker.py — the OCPI chokepoint
def prepare_ocpi(
    message: OCPIMessage, redact: OCPIRedactor | None, max_capture_bytes: int
) -> tuple[BufferedMessage | None, DropReason]:
    if not message.identity.valid():
        return None, DropReason.INVALID_IDENTITY

    source = message.data
    request_body = coerce_body(source.request_body)
    response_body = coerce_body(source.response_body)
    if len(request_body or b"") > max_capture_bytes:
        return None, DropReason.OVERSIZE
    if len(response_body or b"") > max_capture_bytes:
        return None, DropReason.OVERSIZE

    # Take ownership before redacting. From here the exchange is the SDK's,
    # so the redactor may rewrite it in place, and the host may reuse or
    # mutate what it passed the moment the capture call returns.
    message.data = HTTPExchange(
        method=source.method,
        url=source.url,
        status_code=source.status_code,
        request_headers=header_map(source.request_headers),
        response_headers=header_map(source.response_headers),
        request_body=request_body,
        response_body=response_body,
    )
    if redact is not None:
        message = redact(message)
    return BufferedMessage(captured_at=now_iso(), message=message), DropReason.NONE

Four things happen here, in order:

  1. Validate the identity. OCPI needs platform_id and platform_name; OCPP needs charger_id. Tenant is all-or-nothing — both tenant_id and tenant_name, or neither. A message the SDK cannot attribute is useless downstream, so it is dropped rather than shipped as an orphan.
  2. Enforce the byte cap. An oversize body drops the whole message, never a truncated one. Half a JSON body is unparseable, and worse, truncation could slice a credentials payload in a way that defeats the redactor below.
  3. Take ownership. Bodies are normalized to bytes and both header mappings are copied, so the buffered capture shares nothing mutable with the host.
  4. Redact, then stamp captured_at and wrap the message in its envelope.

5.1  What ownership costs in Python

This is the step where the Go SDK does the most work and Python does the least, and the reason is the type system rather than the design. Go's []byte is a view onto memory the caller may reuse the moment the call returns, so the Go chokepoint copies every body and exposes SetRequestBody / SetResponseBody to make the transfer explicit. Python's bytes is immutable: holding the same object is ownership.

_types.py — one function, and mostly a no-op
def coerce_body(value: BodyInput | None) -> bytes | None:
    """Normalize a caller's body to immutable bytes, or None when empty."""
    if value is None:
        return None
    if isinstance(value, bytes):
        return value or None          # already ours — no copy
    if isinstance(value, str):
        return value.encode("utf-8") or None
    return bytes(value) or None       # bytearray / memoryview — copied

So the common case — a framework handing you bytes — costs one isinstance check and nothing else, where Go pays a memcpy per body. The mutable inputs (bytearray, memoryview, the buffer a pooled reader hands back) are copied exactly once, here, and a str is encoded once rather than at serialization time.

The header mappings are still copied, and they have to be. A dict is mutable, and a capture is held until the next flush — up to flush_interval. A host that reuses one header dict per request, or mutates it after the response, would otherwise have whatever it contained five seconds later serialized in its place. Silent, intermittent, and indistinguishable from an SDK bug. The copy also stringifies keys and values, so a header mapping holding an int content-length does not fail at json.dumps time, on the worker thread, where nobody can see it.

OCPP has one extra rule. The ingestion contract requires both direction and raw_frame when event_type is 2 (MESSAGE), so a message event missing either is dropped at the chokepoint rather than being sent and rejected.

5.2  Redaction

Redaction is a closure built once per client — make_ocpi_redactor captures the allowlist set so it is not rebuilt per message — and applied as a transform over a message the chokepoint already owns, so it rewrites in place. OCPI has two rules:

  • Header allowlist. Only listed headers survive; every unlisted header is dropped, so Authorization, Cookie and X-API-Key fall off without needing to be enumerated. ocpi_allowed_headers extends the list and can never shrink it. The default set is twelve headers, none of which can carry a secret: the four OCPI routing headers, content-type / accept / user-agent, two tracing headers, and three pagination ones. An allowlist rather than a denylist, because a denylist silently fails open when a partner invents a new auth header.
  • Credentials-token mask. The OCPI /credentials endpoint exchanges bearer tokens in the request body, where a header allowlist cannot reach. On a URL ending /credentials the token field is replaced with [redacted] — at the root for requests, under data for the response envelope. Any miss (non-credentials URL, non-JSON, no token, invalid UTF-8, re-encode failure) returns the original bytes unchanged: redaction never silently drops data it could not safely rewrite.

OCPP frames are captured verbatim, so there is no OCPP redactor at all: the client's _redact stays None and the chokepoint skips the step, rather than paying a call per frame to run an identity transform. The None-able argument is the seam — masking idTag in Authorize, say, arrives as a make_ocpp_redactor in _redact.py plus one line in start_ocpp, with nothing in the worker or the client to change.

6The buffer

A byte-bounded, drop-oldest queue over a collections.deque. It does no I/O and knows nothing about protocols; it is a bounded handoff between many producers and one consumer.

Why bytes, not a message count. Captured messages vary by two orders of magnitude. A message count is a proxy for the thing an operator actually has to provision, and a poor one — the same 10 000 slots is 3 MiB of heartbeats or 625 MiB of capped bodies. You cannot size a container against a number that is 100× off in the common case.

Typical messageAccountedFit in 32 MiBA 10 000-slot ring
OCPP heartbeat334 B100 46210 000
OCPP meter values577 B58 15310 000
OCPI CDR push (2.4 KiB body)3 064 B10 95110 000

Byte-bounding is strictly better on both axes: the worst case drops from 625 MiB to 32 MiB, and the small messages that dominate real traffic get up to 9× more headroom. The deque also grows on demand, so a 50-charger deployment holds a few hundred kilobytes rather than pre-allocating for its ceiling.

Drop-oldest rather than drop-newest is a deliberate choice: during an incident the most recent frames are the ones an operator actually wants. The producer never learns that eviction happened — there is nothing useful it could do with that information, and returning an error would push a decision onto a caller who called a fire-and-forget method. The operator can act on it, though, which is what the counters in §12 are for.

A deque does the bookkeeping a Go slice needs by hand. popleft() is O(1) and releases the reference as it goes, so there is no zeroing to remember and no compaction step; the Go SDK has both, and a bug in either would pin every message the buffer ever held. What remains is the running byte total, decremented on the way out and incremented on the way in, under the same lock.

Accounting charges each message its variable-length parts plus a deliberately generous fixed overhead (256 B) for the envelope, the object header and the deque slot. Over-counting is the safe direction: it keeps the configured budget a true ceiling. The constant matches the Go SDK's, so the two report comparable footprints for the same traffic. It also means the byte bound implies a message bound — 32 MiB can never hold more than ~131 000 messages however small they are — so there is no second knob to set.

enqueue() returns the resulting message count. That return value is what lets the worker sleep instead of poll, which is §7.

7The worker

One daemon thread, one loop, and no polling. An earlier revision of this SDK woke every 200 ms to check a counter — the shape the Node SDK uses, because JavaScript has no way for a producer to wake a sleeping consumer. Python does: threading.Event.wait(timeout) is both a timed sleep and a wakeable one, so the loop sleeps until the flush interval elapses or a producer has a full batch ready, whichever comes first.

_worker.py — the loop
while True:
    timeout = max(0.0, min(next_flush, next_report) - time.monotonic())
    woke = self._wake.wait(timeout)
    if self._stopped:
        return
    if woke:
        self._wake.clear()

    now = time.monotonic()
    # Every flush restarts the interval: whatever the reason, the
    # buffer is empty afterwards, so a tick already pending would be
    # a no-op.
    if woke or now >= next_flush:
        self.flush_once()
        next_flush = time.monotonic() + interval
    if now >= next_report:
        self._report_health()
        next_report = now + REPORT_INTERVAL

7.1  The size trigger

A producer that fills a batch sets the Event and returns. Setting an Event that is already set is a no-op, so a thousand producers arriving at once collapse into a single wakeup; none of them waits, and the worker does one flush rather than a thousand.

_worker.py — the producer side
def _enqueue(self, envelope: BufferedMessage) -> None:
    """Buffer the envelope and raise the size trigger once a batch is full."""
    if self._buffer.enqueue(envelope) >= BATCH_CAP:
        self._wake.set()

7.2  Flush and drain

flush_once() runs on whatever thread calls it, under an RLock the worker also holds while flushing. A concurrent caller therefore queues behind the in-flight flush rather than starting a second one. This is the one place Python needs a lock where Go does not: Go's flushes are serialized structurally because they all happen on the one goroutine, reached through a channel. Python could copy that — a request queue and an ack — but a lock is fewer moving parts for the same guarantee, and the ack channel exists in Go mostly to avoid blocking a goroutine that has other work.

close() moves the drain onto the caller's thread. The sequence is: set the stop flag and the Event; join the loop (which also waits out a flush already in flight); then drain the remaining buffer in a loop until it is empty or the deadline passes.

_worker.py — shutdown
thread = self._thread
if thread is not None and thread.is_alive():
    thread.join(timeout=max(0.0, end - time.monotonic()))
    if thread.is_alive():
        # The thread is a daemon, so it cannot outlive the process;
        # the in-flight POST it is stuck on has its own timeout.
        self._report_shutdown(drained=False)
        return False

# The loop is gone, so the final drain runs on the caller's thread.
while len(self._buffer) > 0:
    if time.monotonic() >= end:
        self._report_shutdown(drained=False)
        return False
    self.flush_once(deadline=end)

The deadline is passed down into the transport, not just checked between flushes. A Python thread cannot be cancelled from outside — Go aborts its in-flight POST by cancelling the request context — so the bound has to be respected by the code doing the work: the transport starts no attempt past the deadline, skips a backoff sleep that would cross it, and clamps each socket timeout to the time remaining. That is what keeps close(timeout=2) honest.

8The transport

Hand-rolled over urllib.request. No generated client and no HTTP library: two endpoints do not justify putting a dependency — and its transitive tree, and its CVE feed — into a customer's production environment. urllib also reads HTTPS_PROXY and NO_PROXY from the environment the way an enterprise deployment expects, which a hand-rolled http.client would have to reimplement.

The transport owns retry entirely. The worker calls send() once and moves on; there is no retry logic anywhere else, and no caller ever sees a delivery error.

KnobValueWhy
Batch cap1000The ingestion API's maxItems; also the size-based flush trigger
Max attempts5Bounded, so a dead upstream cannot pin the thread indefinitely
Backoff500 ms → 30 sCapped exponential with full jitter, so restarts don't synchronize
Per-attempt timeout30 sA hung connection feeds the backoff instead of stalling the worker
Compression floor1024 BBelow this, compression costs more CPU than it saves bytes

None of these are configurable, and that is intentional. They are properties of the ingestion contract, not of a deployment, and every SDK must agree on them or the API's capacity planning stops meaning anything.

The codec is chosen, not configured. The ingestion API accepts gzip and zstd. zstd is better on both CPU and ratio, but it is a compiled dependency; gzip is in the standard library. So the SDK uses zstd when zstandard is importable and gzip otherwise, decided once and cached. The Go SDK has no equivalent choice — its zstd implementation is pure Go, so it always has one — and neither exposes a compression field, because a body the server rejects is not a trade-off worth offering.

Each client builds its own OpenerDirector rather than calling urlopen, so a host that installed a global opener does not end up routing the SDK's batches through it — and the proxy environment is read once, at construction, rather than per request.

9Wire contract

Both endpoints take {"messages": [ … ]} with flat, snake_case records. The SDK's internal types are deliberately not the wire types — record() maps between them — so the ergonomic Python shape and the ingestion shape can evolve independently. The wire records are TypedDicts, which cost nothing at runtime and let mypy catch a field that drifts from the spec.

Three conventions matter, and all three are shared with the Go SDK:

  • Absent means null, never a zero value. Optional fields are T | None and are always present in the JSON. A missing status code must serialize as null, not 0 — the difference between "no response" and "status zero" is real, and a dropped key would make it invisible.
  • Bodies are base64, always. Both OCPI HTTP bodies and OCPP wire frames. The ingest server decodes before persistence, so downstream consumers see plain UTF-8; encoding keeps the contract uniform across protocols and binary-safe for whatever comes next (ISO 15118 EXI, OCPP 2.0.1 security extensions).
  • Timestamps are RFC 3339, UTC, millisecond precision. Formatted from an aware UTC datetime with a literal Z. The server normalizes anyway; matching it exactly keeps round-trip tests meaningful.

Durations are float seconds — Python's unit for time.sleep, Event.wait and socket timeouts — rather than the Go SDK's time.Duration or the Node SDK's milliseconds. Each SDK uses the unit its runtime already speaks; the defaults are the same wall-clock values in all three.

Config resolution is also where Python has to be more defensive than Go. A Go config cannot contain a string where an int belongs; a Python one can, and the field most likely to hold a surprise is ocpi_allowed_headers, where a bare string is a plausible mistake and iterating it would allowlist twelve single characters. So each tunable checks its type, falls back to the default, and says so — and the warning goes through a sink that swallows exceptions from the host's own logger, because a broken logger must not be able to fail config resolution.

11Lifecycle

the whole lifecycle surface
panda = evpanda.start_ocpi(config)   # never raises, always usable
if panda.error:                      # a ConfigError instance, or None
    log.warning("%s (running inert)", panda.error)

panda.flush()                        # deliver now, wait for it
drained = panda.close()              # drain within drain_timeout
drained = panda.close(timeout=30)    # …or your own deadline

with evpanda.start_ocpp() as panda:  # closes on the way out
    ...

An inert client is a real client. When start_* fails it returns a client with no worker. Every capture method is a no-op, flush() does nothing, close() reports a clean drain, connection() still hands back a usable session, and the adapters fall back to serving requests untouched. This is why the constructor returns a client plus an .error rather than raising: a telemetry SDK must never be the reason a charging platform won't boot.

Close is idempotent, and post-close captures are safe. The client detaches its worker under a lock, so the second close() sees nothing to do and returns the first call's answer. A capture that arrives after close finds no worker and returns. Both are ordinary, expected paths — not error conditions.

The return value means drain, not delivery. close() returns False when the deadline expired with messages still buffered — meaning some telemetry was dropped on the way out. It does not report delivery failures, which are retried and dropped by design. If you want visibility into those, set log_mode="debug" and each dropped batch is logged with its reason, or read stats().dropped_undeliverable.

typical shutdown
server.shutdown()                     # stop accepting first…
if not panda.close():                 # …then drain what was captured
    log.warning("evpanda: shut down with messages still buffered")

# From async code, hand the blocking drain to a thread:
await asyncio.to_thread(panda.close)

Order matters: drain the SDK after the server stops accepting, or you will be draining a buffer that is still filling.

11.1  The process, not just the client

Two things happen to a Python process that never happen to a Go one, and both would silently break capture. The SDK handles them itself, at module level, for every live client — because both are properties of the runtime rather than of any one client, and neither is something a host should have to remember.

Interpreter exit

The delivery thread is a daemon thread, so it is frozen at interpreter shutdown rather than joined — anything captured since the last flush would go with it. An atexit hook closes every live client, which drains within drain_timeout. Closing is idempotent, so a host that closes its own client pays nothing. For a short-lived script — a migration, a one-off sync — this is the difference between all of its telemetry and none of it.

fork()

gunicorn, uWSGI and every other preforking server fork their workers out of a parent that has already imported the application — and with it, often, the client. Only the forking thread survives a fork, so the child inherits a buffer with no thread draining it, and any lock another thread held at fork time is stuck locked forever. An os.register_at_fork(after_in_child=…) hook replaces every lock, drops the parent's undelivered captures (they are the parent's to deliver, and shipping them from both processes would duplicate every one), zeroes the counters, and starts the thread again.

Without the fork hook the failure mode is the worst kind: a gunicorn --preload deployment captures normally, reports nothing, and logs nothing, because from inside the child everything looks fine. There is a test that forks for real and asserts the child's captures arrive and the parent's do not arrive twice.

12Knowing whether it's working

The SDK discards data in five places by design. Four of them were invisible, which made the single most likely integration bug — an adapter that never resolves an identity — look exactly like a working SDK on an idle system. No error, no log, no signal, and a support ticket that could not be answered.

12.1  Counters

stats() is always available: no log mode turns it off, and it is safe on an inert or closed client (a closed one reports its final totals). The counters live on the client rather than the worker precisely so the lifetime tally survives close().

CounterWhat a high value means
captured = 0The capture path is not wired in
dropped_invalidIdentity resolution is failing
dropped_oversizeBodies exceed max_capture_bytes
dropped_evictedUpstream can't keep up, or max_buffer_bytes is too small
dropped_undeliverableNetwork, API key, or ingestion fault
dropped_faultA bug in the SDK

One counter per root cause is the whole design goal: it turns an open-ended investigation into a lookup, in production, with no redeploy. Stats is a frozen dataclass, so it prints readably in a REPL and feeds Prometheus or OpenTelemetry without the SDK depending on either. It is a pull-based snapshot rather than an emitter for the same reason.

12.2  Logging is on by default, and rate-bounded

The policy, and the hazard it avoids. A silent SDK that captures nothing is indistinguishable from a working one, so the default is not silence — problems are reported without the host switching anything on.

What makes that safe is that the SDK logs the rate, not the event. An adapter that resolves no identity drops on every request; per-event logging would emit at request rate, flood the host's log pipeline, and cost them real money in ingestion fees. Instead: one summary line per minute, carrying everything that happened in the window.

log_modeWhat you get
"silent"Nothing, ever. Counters still work.
"errors"Default. Config problems at startup, plus the once-a-minute summary when captures are dropping.
"debug"Adds per-batch delivery failures, swallowed capture faults, and a close summary even on a clean run.

Leaving log_mode unset consults $EVPANDA_LOG, which is the point: an operator can silence the SDK mid-incident with a restart rather than a code change. An explicit field wins over the environment — matching how api_key resolves — and since most hosts never set the field, the env var still reaches almost every deployment. Anything unrecognised in either falls back to errors; a typo must not be able to silence the SDK, which is the same rule the tunables follow in §10.

The SDK logs to logging.getLogger("evpanda") by default, so a host configures or silences it the way it configures anything else — logging.getLogger("evpanda").setLevel(…), a dictConfig entry, a filter. Nothing is logged at import time, and no handler is ever added: a library that calls basicConfig is a library that hijacked someone's logging setup. The health line rides the worker's existing loop, so reporting costs no extra thread and can never overlap a flush. It reports the delta since the last line, so a fault that stops recurring stops being logged.

13OCPP

OCPP identity is known at connect time — you authenticated the charge point during the handshake — so there is no resolver. The recommended path is a session handle: it mints the connection ID, records the connect, and carries the identity, so per-frame calls carry neither.

a CSMS WebSocket handler
import evpanda

panda = evpanda.start_ocpp()          # endpoint and key from the environment
if panda.error:
    log.warning("%s (running inert)", panda.error)

async def handle_charger(websocket, path):
    # Your own charge-point identification — whatever your CSMS already
    # does at handshake time: parse the path, read Basic auth, check a
    # client certificate, hit your database.
    identity = resolve_charger_identity(websocket, path)
    if identity is None:
        await websocket.close(code=1008)
        return

    with panda.connection(identity) as session:   # records the connect
        async for frame in websocket:             # …and the close on the way out
            session.message(frame, evpanda.OCPPDirection.FROM_CP)

            reply = handle_frame(frame)           # your CSMS logic
            await websocket.send(reply)
            session.message(reply, evpanda.OCPPDirection.TO_CP)

The session is a context manager, which is the Python answer to Go's defer sess.Disconnect(): the disconnect is recorded on the way out of the block, including when the block exits because the socket raised. Frames may be bytes or str — a WebSocket library hands you either depending on whether the frame was text or binary, and both are normalized at the chokepoint.

capture_connect, capture_message and capture_disconnect are the flat primitives underneath, each taking the identity and connection ID directly. Use them where a session handle does not fit — a connection whose lifetime you do not own, or replaying frames from a log.

14OCPI, directly

OCPI traffic flows both ways between roaming partners, and the SDK records each direction separately. The method name sets the direction — there is no direction argument to pass, and no way to get it backwards.

MethodYou are the…Typical case
capture_inbound_messageserverAn eMSP pushes a CDR or session update to your endpoints
capture_outbound_messageclientYou pull a partner's locations, or post a token authorization

Easy to get wrong. Identity is always the partner on the other side of the exchange — never your own platform. Inbound and outbound both. A record attributed to yourself is not wrong at the API, it is just useless.

direct capture
panda.capture_inbound_message(
    identity=evpanda.RoamingIdentity(platform_id="acme", platform_name="Acme Mobility"),
    data=evpanda.HTTPExchange(
        method="POST",
        url="/ocpi/2.2/cdrs",
        status_code=201,
        request_headers={"content-type": "application/json"},
        response_headers={"content-type": "application/json"},
        request_body=b'{"id":"cdr-1"}',
        response_body=b'{"status_code":1000}',
    ),
)

Two keyword arguments rather than Go's OCPIMessageInput{Identity, Data} wrapper: Go bundles them into a struct because it has no keyword arguments, and Python does, so the wrapper type would be a name to learn for nothing. The same reasoning removes OCPPMessageInput.

status_code and both bodies are optional; the header mappings may be left empty. Use this path when you have identity in hand and the adapters do not fit — a framework the middleware cannot wrap, or a replay from an audit log.

15OCPI adapters

The adapters do the assembly for you: collect headers and bodies, resolve identity, call the right method. Four of them, because Python's HTTP layers are four rather than Go's one — two server protocols, two client libraries — and each is thin enough to be read in one sitting.

AdapterDirectionWrapsNeeds
wsgi.WSGIMiddlewareinboundFlask, Django, Pyramid, Bottle, any WSGI appstdlib
asgi.ASGIMiddlewareinboundFastAPI, Starlette, Litestar, Django ASGIstdlib
HTTPXTransportoutboundan httpx.Client (or AsyncClient)httpx
RequestsAdapteroutbounda requests.Sessionrequests

That last point is the one real divergence from the Go adapters, and it is worth spelling out. Go carries identity on a context.Context, which is immutable — a value stamped inside the handler cannot be read by the middleware around it, so ocpi.Middleware must be mounted after auth, and mounting it wrong is the SDK's most likely integration fault. A WSGI environ and an ASGI scope are mutable mappings shared with everything inside them, so the Python adapters read identity at the end of the request and the ordering problem disappears.

inbound — ASGI, with a Starlette-style auth layer
from evpanda.ocpi import set_identity
from evpanda.ocpi.asgi import ASGIMiddleware

@app.middleware("http")
async def authenticate(request, call_next):
    partner = lookup_partner(request.headers.get("authorization"))
    if partner is None:
        return JSONResponse({"status_code": 2001}, status_code=401)
    set_identity(request.scope, evpanda.RoamingIdentity(
        platform_id=partner.id, platform_name=partner.name,
    ))
    return await call_next(request)

app = ASGIMiddleware(app, panda)

The ASGI middleware wraps receive and send: request body chunks are recorded as your application receives them, the status and headers come off http.response.start, and body chunks off http.response.body. Non-HTTP scopes — WebSocket, lifespan — are passed straight through with no wrapping at all. The exchange is shipped in a finally, so an application that raised is still captured with whatever status it managed to send.

The WSGI middleware does the same job against a synchronous protocol: it tees wsgi.input as your application reads it, wraps start_response for the status and headers, and returns an iterable that records the body as the server iterates it. The tee implements every read path rather than delegating them — Werkzeug, and so Flask, reads bodies through readinto; Django reads through read and readline; others iterate the stream. A wrapper that forwards one of those straight to the underlying stream records an empty body while the host works perfectly, which is the worst shape of bug this SDK can have — so there are tests against the real frameworks and not only against the protocol. Capture completes when the response iterable is closed, exhausted, or abandoned, whichever comes first.

Both record the request body as your application reads it, so an application that ignores the body records none — nothing is buffered on your behalf, and a streaming handler is never forced into memory. Bodies are capped at max_capture_bytes; an oversize body on either side drops the whole message rather than storing a truncated one.

outbound — httpx
import httpx
from evpanda.ocpi import HTTPXTransport, use_identity

client = httpx.Client(transport=HTTPXTransport(panda))

# You already looked the partner up to get their Token B —
# scope the identity to the same block.
with use_identity(evpanda.RoamingIdentity(platform_id=partner.id,
                                          platform_name=partner.name)):
    response = client.post(
        f"{partner.base_url}/ocpi/2.2/sessions",
        json=payload,
        headers={"Authorization": f"Token {partner.token_b}"},
    )

Because it is a transport, it captures anything that goes through that client — including a generated OCPI client, as long as it accepts an httpx.Client. AsyncHTTPXTransport is the same adapter over handle_async_request. A request whose body httpx has already materialized is read directly; a streamed upload or download is teed as it passes, so neither is forced into memory twice. A transport error propagates unchanged and captures nothing — there was no exchange to record.

outbound — requests
import requests
from evpanda.ocpi import instrument_session, use_identity

session = instrument_session(requests.Session(), panda)

with use_identity(partner_identity):
    response = session.get(f"{partner.base_url}/ocpi/2.2/locations")

RequestsAdapter is an HTTPAdapter subclass, so it composes with pool sizing and urllib3 retries as usual, and instrument_session is a two-line convenience that mounts it for both schemes. Reading response.content inside the adapter caches it on the response, so the caller still gets the body it was going to get. One documented limitation: a call made with stream=True is captured without its response body, since reading it there would consume the stream the caller asked to handle itself.

All four adapters make exactly one change to a request: they strip the SDK's X-EVPanda-* identity headers before dispatch, so a partner never receives them and your tenant_id / tenant_name stay internal. Stripping happens even on a closed client, so closing mid-flight cannot start leaking them.

16Identity resolution

All four adapters resolve identity the same way, and the order is the point.

Three carriers, because Python's HTTP layers hand you three different places to put a value and no single one covers them all:

  • The request mapping — a WSGI environ, an ASGI scope, an httpx request's extensions. Typed, request-scoped, impossible to leak onto the wire, and shared with everything inside the middleware, which is what makes mount order irrelevant. set_identity(carrier, identity) and identity_from(carrier) are the helpers; the key is the string "evpanda.identity", which is the convention both protocols use for third-party scope keys.
  • A ContextVar, through with use_identity(identity):. This is the carrier for code with no request mapping to hand — an outgoing requests call, or a framework that hides the scope from you. It is task-local under asyncio and thread-local otherwise, and the context manager resets it on the way out, so it cannot leak into the next request on a reused worker thread.
  • The X-EVPanda-* headers, for hosts whose identity is already stamped by an upstream proxy or a different process — and, outbound, for per-call attribution through requests, which has no extension mapping of its own.
ConstantHeaderField
ocpi.HEADER_PLATFORM_IDX-EVPanda-Platform-Idplatform_id — required
HEADER_PLATFORM_NAMEX-EVPanda-Platform-Nameplatform_name — required
HEADER_TENANT_IDX-EVPanda-Tenant-Idtenant_id — optional
HEADER_TENANT_NAMEX-EVPanda-Tenant-Nametenant_name — optional

16.1  Custom resolvers

If identity lives somewhere none of the three reach — a client certificate, a path prefix, your own session store — replace the shipped resolver:

a path-prefix resolver
from evpanda.ocpi import RequestInfo

def by_path(info: RequestInfo) -> evpanda.RoamingIdentity | None:
    if not info.url.startswith("/partners/"):
        return None                       # not captured
    name = info.url.removeprefix("/partners/").split("/")[0]
    return evpanda.RoamingIdentity(platform_id=name, platform_name=name)

ASGIMiddleware(app, panda, resolver=by_path)
HTTPXTransport(panda, resolver=by_path)

The resolver takes a RequestInfo — method, URL, lowercased headers, whatever the adapter's own carrier held, and the framework-native object in info.context for anything else it needs. Go passes the *http.Request itself because in Go there is one request type; Python has four, so the adapters normalize. A resolver that raises is treated as "no identity"; the request is served normally either way, and so is one whose identity fails validation.

Everything above the line in that table is a translation: the same decision, spelled the way the language spells it. The two rows that are genuinely new capability are the identity carriers — a mutable request mapping lets the middleware be mounted anywhere, which Go's context cannot — and the process-lifecycle hooks, which exist because a Python deployment forks and exits in ways a Go binary does not.

Two rows are worth flagging for anyone running both SDKs against the same ingestion API, because they are observable rather than internal: the Python SDK may send Content-Encoding: gzip where Go always sends zstd, and a Python client opens a connection per batch where Go reuses one. Neither changes a record.

BKnown gaps and open questions

Recorded so they are decisions rather than oversights.

Spec disagreement. response_status_code is in the ingestion spec's required list but is not marked nullable — yet all three SDKs send null when the status is absent. If Atlas validates strictly, an OCPI capture without a status code will be rejected. Python matches Go here because Go is the reference, but the spec and the SDKs disagree and one of them should move.

  • A streamed requests response is captured without its body. Teeing it would mean wrapping urllib3's raw response and matching its stream() / read() contract, which is private API in practice. httpx, WSGI and ASGI all tee properly; requests is the one place a body can go unrecorded, and the record still carries the method, URL, status and headers.
  • OCPP redaction is a seam, not a feature. Frames are captured verbatim today. idTag in Authorize is the obvious first candidate.
  • No aiohttp or Tornado adapter. Both are server and client, both have hook points that would work, and neither has been asked for. The Capturer seam is public precisely so one can be written outside this package (§2.2).
  • The counters stay inside the process. §12 makes drops visible to whoever runs the host — but EVPanda's own ingestion API still cannot tell a broken integration from an idle one. Piggybacking the counters onto the ingest request (as a header; counts, not content) would let the dashboard flag a customer whose identity resolution is failing without them lifting a finger. It needs an ingestion contract change, so it is a follow-on — but it is where the counters are heading, and it is why they are shaped as a snapshot.
  • The sink is hard-wired to the ingestion API. Worker.flush_once calls Transport.send directly. Narrowing that to a one-method protocol — take a batch, deliver or drop, never raise — would make "ship to a local collector instead of the cloud" a config change rather than a rewrite. Cheap to do now while there are no callers; expensive once there are.
  • One client per protocol per process is assumed. Running many (per tenant, say) works and is tested, but each carries its own thread and buffer — the memory bound multiplies.
